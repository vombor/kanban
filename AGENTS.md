TypeScript principles
- No any types unless absolutely necessary.
- Check node_modules for external API type definitions instead of guessing.
- Prefer SDK-provided types, schemas, helpers, and model metadata over local redefinitions. For things like Cline SDK reasoning settings, use the SDK's source of truth whenever possible instead of recreating unions, support checks, or shapes in Kanban.
- NEVER use inline imports. No await import("./foo.js"), no import("pkg").Type in type positions, and no dynamic imports for types. Always use standard top-level imports.
- NEVER remove or downgrade code to fix type errors from outdated dependencies. Upgrade the dependency instead.

Code quality
- Write production-quality code, not prototypes
- Break components into small, single-responsibility files. 
- Extract shared logic into hooks and utilities. 
- Prioritize maintainability and clean architecture over speed. 
- Follow DRY principles and maintain clean architecture with clear separation of concerns.
- In `web-ui`, prefer `react-use` hooks (via `@/kanban/utils/react-use`) whenever possible
- Before adding custom utility code, evaluate whether a well-maintained third-party package can reduce complexity and long-term maintenance cost.

Architecture opinions
- Avoid thin shell wrappers that only forward props or relocate JSX for a single call site.
- Prefer extracting domain logic (state, effects, async orchestration) over presentation-only pass-through layers.
- Do not optimize for line count alone. Optimize for codebase navigability and clarity.

web-ui Stack
- Kanban web-ui uses Tailwind CSS v4 for styling, Radix UI for accessible headless primitives, and Lucide React for icons.
- Custom UI primitives live in `src/components/ui/` (button, dialog, tooltip, kbd, spinner, cn utility).
- Toast notifications use `sonner`. Import `{ toast }` from `"sonner"` or use `showAppToast` from `@/components/app-toaster`.

Styling mental model
- Use Tailwind utility classes as the primary styling system. Prefer `className` over inline `style={{}}`.
- Prefer Tailwind classes over adding custom CSS in `globals.css` when possible. Conditional Tailwind classes via `cn()` are better than CSS overrides for state-driven styling (e.g. selected/active variants). Reserve `globals.css` for things Tailwind can't express: complex selectors (sibling combinators, attribute selectors), app-level layout glue, or styles that genuinely need to cascade.
- Only use inline `style={{}}` for truly dynamic values (colors from props/variables, computed positions from drag-and-drop, runtime-dependent dimensions).
- The design system tokens are defined in `globals.css` inside `@theme { ... }`. Use Tailwind utilities that reference them: `bg-surface-0`, `text-text-primary`, `border-border`, etc.

Dark theme
- The app is always in dark theme. Colors are set via CSS custom properties in `globals.css`.
- Surface hierarchy: `bg-surface-0` (app background) -> `bg-surface-1` (raised panels) -> `bg-surface-2` (cards/inputs) -> `bg-surface-3` (hover) -> `bg-surface-4` (pressed).
- Do NOT use Blueprint, Tailwind's light-mode defaults, or any `dark:` prefix. The theme is always dark.

Misc. tribal knowledge
- Kanban's native Cline agent is powered by the installed `@clinebot/core` and `@clinebot/llms` packages plus the local `src/cline-sdk/` boundary layer, so when Cline behavior is unclear, inspect those packages and `src/cline-sdk/` for the real implementation details.
- Kanban is launched from the user's shell and inherits its environment. For agent detection and task-agent startup, prefer direct PATH checks and direct process launches over spawning an interactive shell. Avoid `zsh -i`, shell fallback command discovery, or "launch shell then type command into it" on hot paths. On setups with heavy shell init like `conda` or `nvm`, doing that per task can freeze the runtime and even make new Terminal.app windows feel hung when several tasks start at once. It's fine to use an actual interactive shell for explicit shell terminals, not for normal agent session work.
- If CI hangs on Node 22 after tests seem to finish, suspect a live subprocess or SDK-host startup path before assuming a slow test body. Read `.plan/docs/node22-ci-hanging-tests-investigation.md` before repeating that investigation. `test/runtime/cline-sdk/cline-task-session-service.test.ts` was the big prior culprit because a unit-style suite was still booting the real Cline SDK host.
- When Kanban runs on a headless remote Linux instance (for example over SSH+tunnel), native folder picker commands may be unavailable (`zenity`/`kdialog`). Treat this as a normal remote-runtime limitation and use manual path entry fallback instead of requiring desktop packages.
- Moving a card to Done has exactly one implementation: `src/server/task-trash-workflow.ts` (stop task + detail-terminal sessions, start linked backlog tasks, delete the worktree with its patch). The CLI `task done|trash` and the browser call it over tRPC `workspace.trashTask`; the auto-review reconciler calls it in-process. Don't add Done side effects in a caller. The workflow is the only writer of the Done move: the browser shows it optimistically but `useWorkspacePersistence` keeps it out of every save (`holdPendingDoneMove`, see `web-ui/src/state/pending-done-moves.ts`) and flushes pending edits before calling `trashTask`, so no browser save can conflict with the runtime's write. Its `doneGate` is the `qa` landing step (`src/server/task-landing-gate.ts`): on a landing-mode-`qa` workspace it squash-lands a dev card onto its base before Done, and refuses a Done with no `landing: "land" | "discard"` choice when the worktree has work not on the base (`landing.decision: "required"`; the browser then asks "land or discard?"). So a new caller of `trashTask` that finishes a pipeline card must pass a choice, or its Done is silently refused. The same gate covers every other workspace for a human's Done (triggers `cli`/`browser`/`approve`) on a dev or plan card (`isProjectWorkCard`) Kanban doesn't land (issue #11): unpushed work not on the base (`isSnapshotPushed` in land.ts) refuses it with `landing.decision: "discard_required"` until `landing: "discard"`, and the browser asks with the same dialog minus Land. `auto_review`/`pipeline`/`watchdog` finish cards whose work they own and pass, so a new human-facing Done trigger goes into `HUMAN_TRIGGERS` (task-landing-gate.ts), and a new in-process caller that drops a card's work on purpose must say `discard`. Before any land (a `land` choice or an approve, every trigger), right after the hold check, it asks the kit's landing vetoes (`src/kits/land-veto.ts`, one per feature, asked only where the workspace's kit lists that feature; default `createBuiltInLandVetoes()`): the team kit's `runoffs` veto refuses a decided runoff's loser (`landing.decision: "refused"`, shown by the browser as a toast), so the core never reads runoffs.json. A command that changes something before its Done (release-hold lifts the hold) or finishes several cards (a column `--land`) asks the same rule first through `createLandVetoPrecheck()`, so a refused command has no side effects; don't copy the rule into a caller. A discard is never vetoed; only `kanban task handback` keeps its own check, since it lands nothing. Over tRPC only the triggers `cli`/`browser`/`approve` are accepted; `pipeline`/`hold_release` are in-process (the worker asks through its `finishTask` IPC request), and the API validator copies fields one by one (`parseTaskTrashRequest`), so a new request field must be added there too. Every run (any status) and every task delete appends a line to `<home>/data/<ws>/task-history.jsonl` (`src/state/task-history-log.ts`, read with `kanban task history [<id>]`): the workflow's `recordHistory`, the `workspace.deleteWorktree` route (which now stops the card's sessions itself; callers pass `trigger`/`fromColumnId`/`role`, copied in `parseWorktreeDeleteRequest`) and prune-done. tRPC callers hand the workflow `resolveCaller` (the strict caller, a /proc trace at call time, so it is started before any session stops: `startTaskHistoryCallerLookup`), in-process ones log `caller: null`; a new Done or delete path must log there too, or the next "who moved it?" (foo's a5e91/257a4 at the 10/07 restart) has no answer.
- Process cleanup lives in `src/server/process-reaper.ts` (match by /proc cwd/exe inside a worktree + the session tree captured before the session stops; SIGTERM → SIGKILL; never PID 0/1/2, kernel threads, the server or its ancestors, zombies, or reused pids). Kernel threads come from PF_KTHREAD, never "child of PID 2": in the pod PID 2 is the Kanban server, so that rule hid every agent PTY. A process's cwd only says which card started it, not who uses it: the Cline hub daemon (`--cline-hub-daemon`) sits in the worktree of the first Cline card and serves all of them, so it, anything with incoming TCP connections from outside the card, accepted connections on a named unix socket, or children in another worktree is only reported as `shared*`, never signalled and `src/server/orphan-process-sweeper.ts` (periodic sweep, `processes.reaper` in config.json). Done, task delete (`workspace.deleteWorktree`) and project removal reap through `prepareTaskProcessReap` in `runtime-server.ts`, always before the worktree is deleted. Process-group or parent-chain kills are not enough: agents start dev servers with nohup/setsid. Only cards that are Done on a readable board are reaped, even with a deleted cwd; missing/unknown/unreadable-board cards are only reported, because a second Kanban home (e.g. a dev instance with another `KANBAN_HOME`) sees the same legacy worktree roots with its own boards. Tests inject a fake process table (`test/utilities/fake-process-table.ts`); never let a test reap anything outside its temp roots.
- Routing (which agent and model a new card gets, whether a card gets QA and from whom, what happens after a FAIL) is a per-project routing kit, never core code: `kits/default.json`/`kits/team.json` plus user kits in `$KANBAN_HOME/kits/`; the `team` kit is the workflow only and takes its models from a preset (`kits/presets/{cloud,cline,lemonade}.json`, stored as `workspaces.<id>.kit.preset`) or, for a custom team (`preset: null`), from the project's own role settings (`kit apply team --custom` needs `roles.dev.agent` and `roles.qa.agent`, `describeCustomTeamGap` in apply-kit.ts). A preset may hold only model keys (roles' agent/provider/model/tier/note, tiers and their notes, plan candidates, the price region, provider-fact `recommends.settings`): `kitPresetSchema` refuses any workflow key, so every preset and custom team runs the same workflow (user, 2026-10-12: one fixed behaviour each, never derived from the provider; the fallback starts without approval, paid or free). Layers are default ← kit ← preset ← project overrides (`resolveKitLayers`; `recommends.settings` merge as a union by key); messages and logs name a workspace's kit by `kitLabel` (`team (cloud)`, `team (custom)`), logic by `kitName`. These are merged with `workspaces.<id>.kit.overrides` by `src/kits/resolve-kit.ts` and answered by `src/kits/policy.ts`. A kit is the team definition: `roles.<role>` (dev, qa, plan, fallback) with a default model each, and the flow (`onFail`, `fallback.on` triggers and `fallback.requireApproval`, QA, features). The overrides are the project settings, limited to the models the kit names (`roles.<role>.agent|provider|model|tier` and `PROJECT_MODEL_KEYS`: tier picks, QA route reviewers, plan candidates, runoff racers, addressed by list index `tiers.dev.0.model`, which `applyOverride` in resolve-kit.ts follows into the merged list and never grows) and project facts (`PROJECT_FACT_KEYS` in `src/kits/project-settings.ts`); every other key is refused for a project. A new kit field that names a model goes into the lists behind `PROJECT_MODEL_KEYS`, or a project can't set it. Switching kits (`kit apply`) goes through the same route (tRPC `kit.applyKit`, the same caller rule; in-process only without a server and without a session credential) and drops the stored settings that don't fit the new kit; its `--landing` and team-key `--unset` stay the user's. They change only through tRPC `kit.set`/`kit.unset` (`kanban kit set|unset`, `src/trpc/kit-settings-api.ts`: strict caller, the user or that workspace's orchestrator, never a card), logged to `data/<ws>/kit-settings-history.jsonl`; `kit apply --set` uses the same key check. Read roles only through `src/kits/kit-roles.ts`, never `kit.roles` or a legacy key: the legacy keys (`dev.*`, `qa.default`, `plan.agent/model`, `escalate.*`, `onOutage.*`) are translated per layer by `src/kits/kit-legacy-keys.ts` before merging, so a resolved kit never has them (the full schema refuses them), while foo's pre-split overrides keep applying until the user runs `kanban kit migrate-overrides` (doctor warns, never `--fix`). A new role or fact key needs its entry in kit-schema.ts and the project-settings list, or `kit set` refuses it. A workspace without a `kit` entry is on `default` (no routing); nothing is inherited from another workspace. Core code decides on a card's effective agent (`resolveEffectiveAgent()` in `src/core/effective-agent.ts`: session agent > `card.agentId` > selected agent), never on the literal `card.agentId` (a card with no `agentId` runs on the selected agent; misreading that QA'd and landed a whole board on 2026-10-06). The built-in kits are JSON imports bundled into `dist/cli.js`, so editing `kits/*.json` needs a rebuild. A renamed built-in kit (`team-cloud`/`team-local`/`team-cline` → `team` with preset `cloud`/`lemonade`/`cline`, 2026-10-12) keeps its old name only in `src/kits/renamed-kits.ts`, which maps it to a `{ name, preset }` pair: `workspaceKitRefSchema` reads a stored old name as the new pair (so every reader of `settings.kit.name` sees the new name, while raw config.json keeps the old one until doctor `--fix`/`migrateLegacyConfigKeys()` rewrites it), `resolveKitByName` answers the old name with "is now team (<preset>)", and `isReservedKitName` keeps it from user kits; code that reads `kit.name` from the raw config entry (the kit-settings write) must map it through `getRenamedKit` too. Local (Lemonade) model ids are bare family names with dots in their version (`GLM-4.7-Flash-GGUF`), so `getModelVendor()` (policy.ts) reads them through `BARE_MODEL_FAMILIES`, not the Bedrock `<vendor>.` prefix (which read `glm-4`); a new local family that QA's `requireDifferentVendor` must tell apart goes there. ClinePass's `cline-pass/<model>` ids are read after `GATEWAY_MODEL_PREFIX` through the same list. A turn on a local provider (`LOCAL_PROVIDER_IDS` in bench/prices.ts) is priced at 0 by provider, because no id pattern in prices.json can tell a local model from a paid one. A kit's `recommends.settings` are core settings it needs (team: recovery `on`; the lemonade preset adds the Cline turn detector `on`): shown by `kit show`, warned about by doctor, never applied. Lemonade keeps `max_loaded_models` LLMs resident (`/api/v1/health` `max_models.llm`, default 1; container env `LEMONADE_MAX_LOADED_MODELS`); `models.providerCapacity.lemonade.maxLoadedModels` must equal it (above: thrash, below: QA waits for nothing), which `src/kits/local-residency.ts` checks for doctor and `kit show`. Kanban keeps no list of allowed models (the vetted model registry was removed, user decision 2026-10-12; docs/team/MODELS.md): any model may be on any role, nothing in routing refuses or warns about one, and a new routing path must not add such a check. For Cline cards the allow list is Cline's own models.json (a provider's `models` record, no `modelsSourceUrl`), curated by hand by the Kanban orchestrator with models that passed `kanban models vet` (which only writes a report); doctor only warns about a Cline role or card on a model the record lacks (`src/doctor/cline-models-allow-list-checks.ts`), and `kanban setup-provider` never adds or removes a record's model.
- In Progress ↔ Review moves have one writer: `src/server/session-column-sync.ts` (setting `sessionSync`, default on, read once at startup by `src/config/session-sync-config.ts` for both the server and the browser; the browser's moves in `use-board-interactions.ts` run only when it is off; see `docs/fork/session-sync.md`). It runs on session state changes plus a 10 s sweep, and moves a card only when the summary is newer than the card (`updatedAt` guard). It never moves a Review card that auto-review has armed (`pendingGitAction`) to In Progress: the reconciler's own prompt makes the session run, and the reconciler disarms any armed card that leaves Review, so the card would never reach Done. Code that decides a turn has ended (for example the cline-cli turn detector) must end the turn in the session state machine (`transitionToReview`) and let session sync move the card. Moving only the card leaves a Review card whose summary says "running", and that card gets moved straight back to In Progress (the legacy kit's calibration-card bounce, 10/06).
- Review is not "the turn is over". Copilot `--autopilot` flips a card to Review for ~100 ms on every continuation, and a background shell can start a new turn ~6 s after the final stop; other agents can resume quickly too. Code that acts on finished work (snapshot/QA queue, QA ingest, PASS landing, rework "returned", recovery's Review nudges, auto-review's commit prompt) must ask `isReviewSettled(session, now, reviewSettleMs)` (`src/terminal/review-settle.ts`), not `state !== "running"` or the column. Its clock is the summary's `stateChangedAt` (written only by `updateSummary` in the session manager), a later `startedAt` or `lastHookAt`. Output doesn't count, since idle TUIs repaint. `sessionSync.reviewSettleSec` (default 12) is read once at server start; the server passes it to auto-review and puts it in every pipeline snapshot (`reviewSettleMs`), so the worker never reads it from config. The worker host sends an extra snapshot once a Review has settled. The column move stays immediate, and session sync is still the only writer of In Progress ↔ Review moves.
- A Cline CLI (cline 3.x) card can sit "running" with its TUI idle: some providers (Lemonade/llama.cpp) end the turn without the TaskComplete hook, and a no-images rejection leaves Cline's own session file "running". `src/terminal/cline-turn-monitor.ts` reads Cline's session files (matched by the summary's `workspacePath`, not the task id) and ends the turn through the same hooks ingest `to_review` path; `agents.cline.turnDetector.mode` is `report` by default while the legacy kit's column-sync still does this. Session sync's "running in Review → back to In Progress" rule asks `evaluateClineTurnEnd({ requireStatus: false })` first for Cline CLI cards (effective agent), or an open idle TUI bounces the card out of Review; both read session files through `src/terminal/cline-turn-check.ts`, so a lookup change goes there. That check only holds the card in mode `on`. Cline 3.x runs the `.cline/hooks` scripts in its shared hub daemon with the daemon's env, which is the env of the first Cline card, so `KANBAN_HOOK_TASK_ID` there names that card for every Cline card's hooks (foo 27549 bounced to In Progress on its QA card's TaskStart, 10/07). Every Kanban Cline hook must carry its own card identity and never take it from the env or the daemon's cwd: the notify/ingest commands pass `--task-id`/`--workspace-id` (`createHookRuntimeArgs`) plus `--workspace-root <the card's worktree>`, the guard's policy names `worktreePath`, and each checks that against the payload's `workspaceRoots[0]` (`src/terminal/cline-hook-identity.ts`; cline 3.0.69 sends the session's workspace with every hook event) and refuses a mismatch or a missing root; a launch without a workspace id writes no notify step. Cline reads each session's hooks from that session's `<cwd>/.cline/hooks`, so those files must be the card's own: a project that git-ignores `.cline/` gets it mirrored into every worktree as a symlink to the main checkout, which made all of foo's Cline cards share one hooks dir, each launch rewriting everyone's scripts (4189a judged against 6f756's worktree, 10/07). `ensureCardOwnedClineDir()` (`src/terminal/cline-card-dir.ts`) turns that symlink into a per-card directory before a Cline launch writes anything; a new file Kanban writes per card under `.cline` must be written after it, and one in `hooks/` or `rules/` must carry the Kanban marker so it isn't linked into other cards.
- There is no server-side "create card" route: the browser builds new cards in `use-task-editor.ts` and saves the board, and `kanban task create` writes the board in-process (`mutateWorkspaceState`). So the kit's `devAssignment` (`src/kits/dev-assignment.ts`) is called by each creator: in-process by the CLI, and over tRPC `workspace.getDevAssignment` by the create dialog, which only preselects it (the user's pick wins). A new card creator must call `resolveDevAssignment()` too, or its cards silently skip the kit. The answer is stored on the card at creation and never re-read: clearing a card's agent (`task update --agent-id default`, or the editor's first agent option, which is the selected agent) puts it on the selected agent, not the kit (the notes project's 3d145 still ran on claude after `kit apply team-local`, 10/09). `kanban task reassign` is the one path that asks the kit again for existing cards; its rule is `decideDevReassignment()` in dev-assignment.ts (Backlog dev cards without a session only; a card naming no agent/model or still on its last logged `applied` assignment is the kit's, anything else is the user's pick and kept; logged with `source: "reassign"`), so don't add a second re-routing path elsewhere.
